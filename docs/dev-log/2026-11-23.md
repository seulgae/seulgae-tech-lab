## 51. 모바일에서 발걸음 소리가 다다닥 연사되던 문제 (PR #81, 수정)

**블로그 front matter 초안** (Codex가 그대로 쓰거나 다듬는다)
```yaml
---
title: 슬개기술연구소 — 120Hz 휴대폰에서만 발소리가 미쳐 날뛴 이유
date: 2026-11-23
createdAt: 2026-11-23T10:00:00+09:00
tags: Phaser, Game Loop, Audio, Mobile
summary: 화면 주사율(120Hz)과 물리 주기(60Hz)가 달라 "움직임 0" 프레임이 끼고, 그걸 멈춤으로 본 발걸음 계산이 매 프레임 첫 발을 울렸다. 멈춤을 시간으로 판단해 고쳤다.
category: seulgae-tech-lab
---
```

**증상**
- 모바일에서 걸으면 발걸음 소리가 "다다다닥" 지나치게 빠르게 났다. PC(60Hz 모니터)에서는 정상이었다.

**원인**
- 발걸음 계산(`FootstepTracker`)은 한 프레임이라도 좌표가 그대로면 "멈춤"으로 보고, 다음 움직임을 "첫 발"로 바로 울렸다.
- Phaser Arcade 물리는 초당 60번 고정 간격으로 움직인다. 화면이 90·120Hz인 휴대폰은 그 사이에 화면을 더 그려서, 걷는 중에도 좌표가 그대로인 프레임이 번갈아 끼었다.
- 결과: "멈춤 → 첫 발"이 매 프레임 반복됐다. 재현해 보니 1초 걷기에 60Hz는 7번, **120Hz는 60번** 울렸다.

**해결**
- 멈춤을 프레임이 아니라 **시간**으로 판단한다. 좌표가 0.12초(`STOP_MS`) 넘게 그대로일 때만 멈춘 것으로 본다.
- 장면이 프레임 시간(`delta`)을 넘겨준다. 다른 연구원 발걸음(보간 위치)에도 똑같이 적용했다.
- 벽에 막혔을 때 소리 없음, 다시 걸으면 첫 발, 순간이동 무시는 그대로다.

**주요 소스**
| 파일 | 내용 |
|---|---|
| `frontend/src/audio/soundRules.ts` | `FootstepTracker`: 시간 기준 멈춤 판단 |
| `frontend/src/game/scenes/LabLobbyScene.ts`, `game/multiplayer/LobbyMultiplayer.ts` | 프레임 시간 전달 |
| `frontend/tests/audio.test.mjs` | 60·90·120Hz에서 같은 발걸음 수(회귀 테스트) |

**기술 포인트**
- **주사율과 물리 주기는 다르다**: 고정 간격 물리 + 가변 주사율 렌더링에서는 "이번 프레임에 움직였나"가 걷는 중인지를 뜻하지 않는다. 상태 판단은 시간으로 해야 기기마다 같게 동작한다.
- 테스트는 물리 60스텝과 화면 60·90·120Hz를 흉내 내 같은 결과(1초 7번)가 나오는지 본다. 고치기 전 코드에서는 120Hz가 60번이라 실패한다.

**확인**
- 프론트 테스트 148개, 타입 검사 통과. 실제 120Hz 휴대폰에서 들어 보는 확인은 운영 반영 후 필요하다.

## 54. 서버실 랙 4개 용량 조사: Apache MINA SSHD로 CPU·메모리, JVM 힙·가동시간 (PR #84)

**블로그 front matter 초안** (Codex가 그대로 쓰거나 다듬는다)
```yaml
---
title: 슬개기술연구소 — 회사에서 만든 MINA SSHD 서버 점검을 게임 서버실 랙 4개로
date: 2026-11-23
createdAt: 2026-11-23T18:40:00+09:00
tags: Java, SSH, Apache MINA SSHD, Spring Boot, JVM
summary: 회사에서 JSch 대신 MINA SSHD로 만든 서버 용량 수집을 홈서버에 다시 적용했다. 서버실 랙 4개가 CPU, 메모리, JVM 힙, 가동시간을 나눠 보여 주고, 키 인증·known_hosts·강제 명령으로 SSH 권한을 최소화했다.
category: seulgae-tech-lab
---
```
> 참고 글: 블로그 "JSch가 WEB 서버 앞에서 멈춘 날 — Apache MINA SSHD로 서버 용량 모니터링 만들기"(jsch-to-mina-sshd)

**구현**
- 의존성 `org.apache.sshd:sshd-core:2.16.0`(참고 글과 같은 버전)을 추가했다.
- **랙 4개를 따로**(왼쪽부터) 열고, 랙마다 분류 하나를 보여 준다.
  - **1번 CPU 실시간 사용량**
    - 호스트 사용률(100 − idle)과 user·system·iowait
    - 부하 평균 1·5·15분, 코어 수, 코어당 부하, JVM 프로세스 CPU
    - 80% 초과 경고, 최근 15분 추이
  - **2번 메모리 사용량**
    - (전체 − 가용) ÷ 전체 사용률
    - 전체·사용·가용·버퍼캐시, 스왑, JVM 힙 최대 ÷ 전체
    - 80% 경고, 추이
  - **3번 JVM 힙**: 사용·확보·최대와 사용률, 힙 외, GC 횟수·누적 시간(가동 대비 %), 스레드(최고)
  - **4번 가동시간**: 서버 가동시간·부팅 시각, JVM 가동시간·시작(배포) 시각, 수집 상태·마지막 수집
- 호스트 값은 30초마다 SSH 한 번으로 `nproc`, `/proc/loadavg`, `vmstat 1 2`, `free -b`, `/proc/uptime`을 받는다. JVM 값은 MXBean에서 읽는다. DB 저장 없이 최근 30회만 메모리에 둔다.
- 서버 상태 창의 "방별 인원"을 지웠다.
- SSH 설정이 없으면 JVM 값만 보이고 호스트 자리에는 "설정되지 않았어요"가 뜬다. 운영에서 켜는 방법은 `docs/server-capacity.md`에 적었다.

**주요 소스**
| 파일 | 내용 |
|---|---|
| `backend/.../lab/capacity/SshProbe.java` | MINA SSHD 접속·EXEC 실행(키 인증, known_hosts, 단계별 10초) |
| `backend/.../lab/capacity/HostMetrics.java` | 프로브 명령과 출력 파싱 |
| `backend/.../lab/capacity/ServerCapacityService.java`, `ServerCapacityController.java` | 30초 수집, 추이, JVM 값, `GET /api/lab/capacity` |
| `deploy/capacity-probe.sh`, `docs/server-capacity.md` | 강제 명령용 프로브, 켜는 방법 |
| `frontend/src/features/lab/components/ServerRackPanel.tsx`, `model/capacity.ts` | 랙별 화면, 게이지·추이 |
| `shared/lobby-world.json` | 랙 상호작용 2개 → 4개 |
| `SshProbeTest.java`, `ServerCapacityTest.java`, `tests/server-capacity.test.mjs` | 테스트 SSH 서버 왕복, 파싱·경고·추이, 랙 연결 |

**기술 포인트**
- **참고 글에서 그대로 가져온 것**
  - 비동기 단계마다 `verify(timeout)`을 둔다.
  - 셸 대신 `CHANNEL_EXEC`을 쓰고 stdout·stderr를 나눠 받는다.
  - `waitFor(CLOSED)` 뒤 TIMEOUT 이벤트와 종료 코드를 검사한다.
  - 채널 → 세션 순서로 닫으며 원래 예외를 보존한다(try-with-resources의 suppressed).
  - `vmstat 1 2`의 두 번째 줄을 쓴다(첫 줄은 부팅 이후 평균).
- **참고 글보다 조인 것**
  - 비밀번호 대신 키 인증을 쓴다.
  - 호스트 키를 known_hosts로 검증하고 모르는 키는 거절한다.
  - 운영 키는 `authorized_keys`의 `restrict,command="capacity-probe.sh"`로 프로브 하나만 실행되게 묶는다. 게임 서버가 털려도 이 키로는 셸을 얻지 못한다.
- **출력에 이름표**: 명령마다 `@nproc` 같은 구역 줄을 먼저 찍는다. 그래서 출력 순서나 `vmstat` 열 순서가 달라도 머리줄로 열 위치를 찾는다.
- **공개 API는 집계값만**: 호스트 이름·IP·계정·명령 원문·오류 원문은 응답에 없고, 실패는 짧은 코드(`CONNECT`, `TIMEOUT`, `EXIT`, `PARSE`)로만 알린다.

**트러블슈팅**
- 증상: API 계약 테스트가 첫 수집 전(시작 5초 안)에 돌면 상태가 `PENDING`으로 나올 수 있었다. → 원인: 미설정 판단을 스케줄 수집에서만 했다. → 해결: 응답을 만들 때 설정이 없으면 바로 `NOT_CONFIGURED`로 알린다.

**확인**
- 백엔드 테스트 115개(건너뜀 5), 프론트 테스트 150개, 타입 검사, 빌드 통과
  - `SshProbeTest`: 같은 MINA SSHD로 띄운 테스트 SSH 서버에 키로 로그인해 EXEC 출력을 받았다. known_hosts와 다른 호스트 키는 거절했고, 종료 코드 2는 실패로 처리했다.
- 로컬 화면: 랙 1~4 창, 게이지·추이. 호스트 값은 응답을 예시 값으로 바꿔 끼워 확인했다. 실제 로컬 API는 `NOT_CONFIGURED`와 JVM 값이다.
- 확인 못 한 것: 운영 호스트에 키·known_hosts를 설정한 뒤 실제 수집은 운영에서 확인해야 한다.

**운영 설정 (블로그에 쓸 때 참고)**
- 순서: 수집 전용 ed25519 키 생성 → authorized_keys에 `restrict,command="…/capacity-probe.sh"`로 등록 → `ssh-keyscan`으로 known_hosts(이름은 `host.docker.internal`) → 컨테이너 uid로 소유자·600 권한 → compose에 `extra_hosts: host-gateway`·환경 변수 4개·키 폴더 읽기 전용 마운트.
- 확인: 4번 랙 "정상 수집 중", 실패하면 로그의 `[capacity]`와 실패 코드표(`docs/server-capacity.md`).
- 설계 메모: compose 변경을 이 PR에 넣지 않은 이유는 키 파일이 없는 상태에서 마운트·환경 변수를 넣으면 배포가 깨지기 때문이다. 키를 먼저 준비한 뒤 compose PR을 따로 낸다.

## 55. 서버 용량 조사 운영 연결: compose에 SSH 설정 (PR #85)

**구현**
- 운영 서버에서 수집 전용 키·known_hosts·권한(컨테이너 uid 10001, 개인키 600)을 준비한 뒤, `compose.yml` backend에 설정을 넣었다.
  - 환경 변수 4개(`LAB_CAPACITY_SSH_HOST`=`host.docker.internal`, 계정, 키 경로, known_hosts 경로)
  - `extra_hosts: host.docker.internal:host-gateway`(컨테이너에서 호스트로 가는 이름)
  - 키 폴더를 `/run/capacity`에 **읽기 전용**으로 마운트
- 키 폴더가 비어 있어도 앱은 그대로 뜨고 랙에 "설정되지 않았어요"만 보인다.

**주요 소스**
| 파일 | 내용 |
|---|---|
| `compose.yml` | 용량 조사 SSH 환경 변수, extra_hosts, 키 폴더 마운트 |
| `deploy/test_compose.py` | 호스트 이름, extra_hosts, 읽기 전용 마운트, 비밀번호 변수 없음 |

**트러블슈팅**
- 증상: `sudo chown -R <uid> …`가 "uid: No such file or directory"로 실패했다. → 원인: `<uid>`를 그대로 입력해 bash가 `<`를 입력 리다이렉트로 읽었다. → 해결: `docker exec <backend> id -u`로 숫자(10001)를 확인해 넣었다.
- 증상: chown 뒤 `chmod 600`이 "Operation not permitted". → 원인: 소유자가 10001로 바뀌어 seulgae 계정이 권한을 바꿀 수 없다. → 해결: `sudo chmod`.
- 증상: 배포 뒤 4번 랙 수집 상태가 `CONNECT`, 로그에 `SSH2_DISCONNECT_HOST_KEY_NOT_VERIFIABLE - Server key did not validate`. → 원인: known_hosts를 `ssh-keyscan -t ed25519`로 ed25519 키 하나만 저장했는데, MINA SSHD가 서버의 ecdsa 호스트 키를 골랐다(일반 `ssh` 명령은 known_hosts에 있는 종류를 골라서 같은 설정으로도 문제가 안 보인다). → 해결: `ssh-keyscan`을 종류 지정 없이 다시 실행해 모든 호스트 키를 저장. 문서 3단계도 고쳤다.
- 증상: 호스트 키를 고친 뒤 로그에 `Failed (NoSuchAlgorithmException) to load key resource=/run/capacity/id_ed25519: Unsupported key type (ssh-ed25519)`. → 원인: MINA SSHD 2.16은 Java 17에서 ed25519 개인키를 `net.i2p.crypto:eddsa` 라이브러리로 읽는데 의존성에 없었다(로컬 테스트는 RSA 키라 드러나지 않았다). → 해결: `eddsa` 0.3.0을 추가하고, 운영과 같은 ed25519 키로 접속하는 테스트를 붙였다(라이브러리를 빼면 이 테스트가 실패하는 것도 확인).

**확인**
- 배포 설정 테스트는 로컬에 docker가 없어 CI에서 확인한다. 실제 수집(4번 랙 "정상 수집 중")은 배포 후 운영에서 확인해야 한다.

**트러블슈팅 (운영 연결 마지막 단계)**
- 증상: ed25519 라이브러리를 배포한 뒤에도 `CONNECT`, 백엔드 로그는 `HostBoundPubkeyAuthentication` INFO만 반복됐다. 호스트 `/var/log/auth.log`에는 `Connection closed by authenticating user seulgae … [preauth]`가 찍혔다. → 원인: 설정 2단계(수집 키를 `authorized_keys`에 강제 명령으로 등록)를 빠뜨렸다(`grep -c stlab-capacity ~/.ssh/authorized_keys` = 0). → 해결: `restrict,command="…/capacity-probe.sh" <공개키>` 줄을 추가하자 다음 수집(30초 안)에 `OK`가 됐다.
- 정리: 이번 연결은 "호스트 키 종류(known_hosts) → 개인키 형식(eddsa 라이브러리) → 키 등록(authorized_keys)" 세 단계에서 차례로 막혔다. 각각 로그 한 줄(`Server key did not validate` / `Unsupported key type` / auth.log의 `[preauth]`)로 구분됐다.

## 61. 테이블 이름 규칙 tb_lab_와 주석, 호환 뷰 (PR #93, 확장 단계)

**규칙(2026-11-23 결정)**
- 테이블은 `tb_lab_<명시적 이름>`이고, 단수형으로 무엇을 담는지 드러나게 짓는다.
- 모든 테이블과 컬럼에 `COMMENT ON`을 단다.

**구현 (V17)**
- 11개 이름 변경
  - 회원·코드: `members→tb_lab_member`, `common_codes→tb_lab_common_code`, `level_requests→tb_lab_level_request`
  - 업무·소지품: `work_items→tb_lab_work_item`, `inventories→tb_lab_member_inventory`, `coin_events→tb_lab_coin_history`, `items→tb_lab_item`
  - 게시판·폰: `guestbook_entries→tb_lab_guestbook`, `meeting_agendas→tb_lab_meeting_agenda`, `todos→tb_lab_todo`, `sns_posts→tb_lab_sns_post`
- 모든 테이블·컬럼에 한글 주석을 달았다.
- 예전 이름은 **호환 뷰**(`CREATE VIEW lab.members AS SELECT * FROM lab.tb_lab_member`)로 남겼다. 지금 돌아가는 V16 앱이 마이그레이션 뒤에도 그대로 읽고 쓴다.

**기술 포인트**
- **이름 변경도 확장 → 사용 → 축소**: 이름만 바꾸면 예전 이름을 쓰는 앱이 즉시 멈춘다. 배포 도구는 "돌아가는 앱이 새 스키마를 지원하지 않으면 마이그레이션 금지"라서, 앱을 잠깐 멈추는 방식도 도구 수정이 필요했다. 그래서 호환 뷰로 서비스를 끊지 않는 쪽을 골랐다.
- **단순 뷰는 갱신 가능**: 한 테이블에 `SELECT *`인 뷰는 PostgreSQL이 자동으로 갱신 가능 뷰로 다뤄, 예전 코드의 INSERT·UPDATE·DELETE·RETURNING이 그대로 된다. CI는 V17을 적용한 DB에서 예전 이름을 쓰는 현재 코드의 DB 테스트와 API 계약 테스트를 돌려 이를 확인한다.
- 인덱스·제약 이름은 바꾸지 않았다(동작과 무관).

**남은 순서**: 이 PR 머지 → 서버 `migrate-prod.py`(V16 → V17) → 코드가 새 이름을 쓰는 PR(V18 호환 뷰 삭제 포함, 17..18) → V18 → 18..18

- 배포 도구(`select_release`)는 호환 여부와 상관없이 **가장 최근 main 릴리스 하나**만 고른다. #94 릴리스(17..18)가 최신이 되자 V16 DB에는 배포할 수 없었다.
- `migrate-prod.py`는 서버 체크아웃(#94로 이동)의 `LATEST_SCHEMA`(18)를 목표로 삼았다. V17을 건너뛰고 V18로 가려 했지만, 돌고 있는 #92 앱이 18을 지원하지 않아 거부됐다.
- 결국 V17로 가는 경로가 없었다. 안전장치가 모두 막아 DB와 서비스는 멀쩡했다.

**해결**
- #94 머지를 되돌리는 PR을 냈다. 최신 릴리스가 다시 #93 상태(16..17, 목표 V17)가 된다.
- 순서: 이 PR 배포 → `migrate-prod.py`(V16 → V17) → #94 내용을 다시 올림(17..18) → V18 → 18..18

**교훈**
- 확장 → 사용 PR은 "확장 머지 → **마이그레이션** → 사용 머지" 순서를 지켜야 한다. 사용 PR은 마이그레이션이 끝날 때까지 Draft로 둔다(머지 버튼을 누르지 않는다).

## 65. 백엔드 패키지를 기능별 계층 구조로 정리 (PR #97)

**요청**
- 예전 MVC 프로젝트처럼 기능 폴더 안을 `controller·dto·entity·repository·service(impl)`로 나누고 싶다. 지금은 한 폴더에 계층이 섞여 이해하기 어렵다.

**구현** (동작 변경 없음)
- 49개 파일을 계층 폴더로 옮기고 이름을 통일했다.
  - 저장소: `XxxStore` → `XxxRepository`(인터페이스) + `repository/impl/JdbcXxxRepository`
  - 회원·회의 안건 저장소: 클래스였던 것을 인터페이스 + Jdbc 구현으로 나눴다.
- 서비스 13개를 **인터페이스 + `service/impl/XxxServiceImpl`**로 나눴다. 공개 상수는 인터페이스로 옮겼다.
- 클래스 안에 숨어 있던 record 58개를 꺼냈다.
  - 요청·응답은 `dto`(이름 끝 DTO)로 옮겼다.
  - 테이블 행은 `entity`로 옮겼다(예: `CoinEvent` → `CoinHistory`, `Entry` → `Guestbook`).
- 테스트도 같은 패키지로 옮겼다(패키지 전용 멤버를 그대로 시험). 쓰지 않는 import 2,930줄을 정리했다.
- 규칙은 `docs/backend-structure.md`에 적었다. 멀티플레이(WebSocket)는 실시간 처리 단위(config·websocket·domain)를 유지했다.

**기술 포인트**
- **스크립트로 옮기고 컴파일러로 확인**: 이동·이름·record 분리·인터페이스 생성을 표(매핑)로 정의한 Node 스크립트로 한 번에 했다. 남은 참조는 `mvn compile` 오류를 기준으로 고쳤다(오류 200 → 58 → 0).
- **의존 방향**: controller → service 인터페이스 → repository 인터페이스. `impl` 패키지는 다른 계층에서 import하지 않는다(스프링 주입).
- 기존 주석은 그대로 두고, 새로 생긴 인터페이스·DTO·엔티티만 주석 규칙(작성자 길태형)을 따랐다.

**확인**
- 백엔드 테스트 102개(건너뜀 1) 통과. 스프링 기동 테스트(로컬 앱)를 포함한다. API 응답 모양은 record 필드가 같아 바뀌지 않는다(CI 계약 테스트로 확인).

## 67. 오른쪽 위 빈 방을 "실습 연구실"로 (PR #99)

- 로비 오른쪽 위 빈 방(office-2, 예전 "뭘 만들까")을 **실습 연구실**로 이름을 바꿨다. 기술 면접 대비 원리 실험 장치(트랜잭션 격리 → 인덱스 → 스프링 원리 → 동시성 순)를 하나씩 들일 방이다.
- 실험 방식: 주제 하나 = 실험 장치 하나. ①라이브러리 없이 핵심을 직접 구현 → ②게임 안 장치로 동작을 시각화 → ③칠판에 "면접 질문 → 내 답"과 개발 로그·블로그.
- 방 안내 문구·펫 팁·폰 길 안내를 바꿨다. 삭제된 "아이디어 일지"를 가리키던 펫 팁도 고쳤다.

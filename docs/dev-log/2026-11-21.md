## 31. 식물 행운: 화분을 흔들면 5% 확률로 1~3원 (PR #54, V8 사용 단계)

**블로그 front matter 초안** (Codex가 그대로 쓰거나 다듬는다)
```yaml
---
title: 슬개기술연구소 — 화분을 흔들면 가끔 동전이 떨어진다
date: 2026-11-21
createdAt: 2026-11-21T12:00:00+09:00
tags: Spring Boot, Game Economy, Randomness, Phaser
summary: 화분을 흔들면 5% 확률로 1~3원이 떨어지는 작은 이벤트를 만들었다. 추첨은 서버가 하고, 연타와 하루 당첨 횟수를 제한했다.
category: seulgae-tech-lab
---
```
> createdAt은 대략 시각이다. 실제 시각은 `git log`로 확인한다.

**구현**
- 화분(로비·회의실·사무실)을 E로 흔들거나 클릭하면, 흔들리는 연출과 함께 서버에 `POST /api/inventory/plant`를 보낸다.
- 서버가 추첨한다. 5% 확률로 1~3원을 주고, 동전 변동 기록 사유는 `PLANT_LUCK`(V8, 30번)이다.
- 당첨되면 "화분에서 동전이 떨어졌어요! +N원" 배너와 기존 동전 연출(머리 위로 동전이 튀어 오름, 땡 소리)이 나온다.
- 남용 방지
  - 2초 안에 다시 흔들면 추첨하지 않는다.
  - 하루(한국 시간) 10번까지만 당첨된다. 하루 최대 30원이다.
- 비회원은 흔드는 연출만 보고 동전은 받지 않는다(401).

**주요 소스**
| 파일 | 내용 |
|---|---|
| `backend/.../inventory/InventoryService.java`, `InventoryController.java` | 추첨(5%, 1~3원), 연타·하루 한도, API |
| `frontend/src/features/inventory/inventoryStore.ts` | `shakePlant`, 동전 이벤트 |
| `frontend/src/game/rooms/RoomFx.ts` | 화분 흔들기 → 추첨 → 배너 |
| `InventoryServiceTest.java`, `tests/inventory.test.mjs`, `backend/tests/research-api.mjs` | 추첨·한도·연타, 화면 결과, 비회원 401 |

**기술 포인트**
- **추첨은 서버에서**: 화면이 "당첨"을 정하면 요청만 조작해 동전을 만들 수 있다. 화면은 흔들었다는 사실만 보내고, 결과는 서버가 정한다.
- **추첨기 주입**: 서비스가 `RandomGenerator`와 시계를 받게 해서, 테스트에서 "당첨 → 3원", "연타 무시", "하루 10번 한도"를 정해진 값으로 확인했다. 운영은 `SecureRandom`이다.
- **연타 기록은 메모리에**: 2초 쿨다운은 서버 메모리(회원별 마지막 시각)로 처리한다. 서버를 다시 시작하면 초기화되지만, 하루 한도는 DB 기록으로 센다.

**확인**
- 백엔드 테스트 86개, 프론트 테스트 120개, 타입 검사 통과.
- 회원 기능이라 로컬(카카오 꺼짐)에서는 화면으로 확인하지 못했다. 운영(V8 적용 후)에서 확인이 필요하다.

## 32. 회의실 아이템 교환과 바닥 아이템 실시간 반영 (이번 PR, QA "아이템 버리면 다른 사람한테 안보임")

**블로그 front matter 초안** (Codex가 그대로 쓰거나 다듬는다)
```yaml
---
title: 슬개기술연구소 — 회의실에서 물고기를 맞바꾸다
date: 2026-11-21
createdAt: 2026-11-21T15:00:00+09:00
tags: WebSocket, Spring Boot, PostgreSQL, Transactions, React
summary: 회의실에서 다른 연구원에게 가방 아이템 교환을 신청하고, 상대가 자기 아이템을 골라 맞바꾸는 기능을 만들었다. 두 아이템의 주인을 한 문장의 UPDATE로 바꾸고, 바닥 아이템도 회의실에서 실시간으로 보이게 했다.
category: seulgae-tech-lab
---
```
> createdAt은 대략 시각이다. 실제 시각은 `git log`로 확인한다.

**배경**: QA 게시판 "아이템 버리면 다른 사람한테 안보임. 회의실에서 교환할 수 있게, 교환 신청 기능도 만들어줘"(2026-11-21).
- 28번(회의실 전용 멀티플레이) 이후 바닥 아이템은 REST로 처리하고, 방에 들어갈 때만 다시 읽었다.
- 그래서 같은 회의실 사람이 버린 아이템이 바로 보이지 않았다.

**구현**
- **바닥 아이템 실시간(회의실)**: REST로 버리기·줍기를 하면 서버가 `GroundChanged` 이벤트를 내고, 소켓 핸들러가 그 방에 연결된 사람에게 `ground`를 다시 보낸다.
- **교환 신청**(로그인 회원, 회의실 연결 중)
  1. 가방 창의 아이템마다 "교환" → 같은 방 연구원 이름을 고른다 → `trade_offer`.
  2. 받은 사람에게 "OO님이 메기 40cm를 내밀며 교환을 신청했어요" 창이 뜬다. 내 가방에서 하나 골라 "맞바꾸기" 또는 "거절"한다(60초 뒤 자동으로 닫힘).
  3. 서버가 두 아이템의 주인을 맞바꾸고, 양쪽에 결과(`trade_status`: 맞바꿈·거절·실패와 이유)를 보낸다. 화면 아래 알림과 가방 새로고침이 따라온다.
- **규칙**
  - 신청은 60초 뒤 사라진다.
  - 한 사람은 한 번에 하나만 보내고 하나만 받을 수 있다.
  - 나에게는 신청할 수 없다.
  - 한쪽이 회의실을 나가면 신청을 취소하고 상대에게 알린다.
  - 비회원은 "로그인한 연구원만" 안내를 받는다.
- 소켓 핸드셰이크에서 다시 세션 쿠키로 회원을 확인한다(`MEMBER_ID`, 28번에서 지웠던 것을 교환용으로 되살림).

**주요 소스**
| 파일 | 내용 |
|---|---|
| `backend/.../multiplayer/lobby/domain/TradeDesk.java` | 교환 신청 대기열(60초, 1인 1건) |
| `backend/.../websocket/LobbySocketHandler.java`, `config/LobbyWebSocketConfig.java` | trade_offer·trade_answer 처리, 결과 알림, 바닥 실시간, 회원 확인 |
| `backend/.../inventory/{InventoryService,JdbcInventoryStore,InventoryController,GroundChanged}.java` | 맞바꾸기(swap), 바닥 변경 이벤트 |
| `frontend/src/features/inventory/{InventoryPanel,TradeOfferPanel}.tsx`, `tradeMessages.ts` | 교환 신청·받은 신청 창·안내 문구 |
| `frontend/src/features/multiplayer/{MultiplayerClient.ts,model/protocol.ts}`, `components/GameCanvas.tsx` | 교환 메시지 송수신·검증, 결과 알림 |
| `TradeDeskTest.java`, `InventoryServiceTest.java`, `LobbySocketTest.java`, `tests/trade.test.mjs` | 대기열 규칙, 맞바꾸기, 비회원 안내, 클라이언트 |

**기술 포인트**
- **두 아이템을 한 문장으로 맞바꾸기**:
  `UPDATE items SET owner_id = CASE WHEN id = :itemA THEN :b ELSE :a END WHERE (id = :itemA AND owner_id = :a) OR (id = :itemB AND owner_id = :b)`
  - 바뀐 행이 2가 아니면 예외로 트랜잭션을 되돌린다.
  - 그 사이 한쪽 아이템을 버렸거나 다른 교환으로 넘어갔으면 아무것도 바뀌지 않는다.
- **신청은 메모리, 결과는 DB**: 60초짜리 신청은 서버 메모리 대기열(`TradeDesk`)에 두고, 확정된 교환만 DB에 남긴다. 스키마 변경 없이 만들었다.
- **REST와 소켓 잇기**: 버리기·줍기는 REST, 실시간 알림은 소켓이다. 둘을 Spring 이벤트(`ApplicationEventPublisher` → `@EventListener`)로 이었다.

**확인**
- 백엔드 테스트 91개, 프론트 테스트 123개, 타입 검사, 빌드 통과(식물 행운 브랜치 포함).
- 로그인 회원 두 명이 필요한 기능이라 로컬(카카오 꺼짐)에서는 화면으로 확인하지 못했다. 운영에서 두 계정으로 확인이 필요하다.

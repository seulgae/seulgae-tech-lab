```yaml
---
title: 슬개기술연구소 — 방마다 다른 상호작용, 서버 상태와 테이블 대화
date: 2026-11-16
createdAt: 2026-11-16T21:16:03+09:00
tags: React, Phaser, Spring Boot, WebSocket
summary: 공유 맵으로 방별 상호작용을 정의하고, 서버 상태·빌드 정보 API와 서버 좌표로 검증하는 근거리 테이블 대화를 추가한 커밋을 코드와 작업 문서로 정리했다.
category: seulgae-tech-lab
---
```

**구현**
- 공유 맵 `shared/lobby-world.json`의 방마다 `interactions`(id·kind·영역·range)를 정의했다. 서버와 클라이언트가 **같은 데이터, 같은 거리식(사각형 가장자리 거리)**으로 판정한다.
- 서버실 랙 → 실시간 서버 상태, 개발 연구실 컴퓨터 → 빌드 정보, 회의 테이블 → 근거리 "테이블 대화".

**주요 소스**
| 파일 | 내용 |
|---|---|
| `backend/.../lab/status/LabStatusController.java` | `GET /api/lab/status`(가동 시간·방별 인원·JVM 힙, `no-store`), `GET /api/lab/build`(build-info + 커밋 7자리, 16진수만 신뢰) |
| `backend/.../multiplayer/lobby/domain/LobbyWorld.java` | `Interaction.near()` 가장자리 거리 판정, `roomIds()`, `near(room, kind, x, y)` |
| `backend/.../multiplayer/lobby/domain/LobbyChat.java` | `Message.scope`(room/table), 테이블 대화는 서버 좌표 검증 + 기록 미저장 |
| `backend/.../multiplayer/lobby/websocket/LobbySocketHandler.java` | 채팅 `scope` 검증, 테이블 범위 안 참가자에게만 전달 |
| `frontend/src/game/maps/rooms.ts` | `nearestInteraction()` |
| `frontend/src/features/lab/*` | `LabInfoPanel`(3초 폴링, 응답 형식 검증), `labApi.ts`, `labTypes.ts` |
| `backend/pom.xml`, `backend/Dockerfile`, `.github/workflows/ci.yml` | `build-info` goal, `GIT_COMMIT` 빌드 인자 → `LAB_BUILD_COMMIT` |

**기술 포인트**
- 근거리 채팅은 **클라이언트가 아니라 서버 좌표**로 수신자를 정한다. 클라이언트가 조작한 위치로 엿들을 수 없다.
- 기존 클라이언트 호환: 일반 채팅은 `scope` 필드 없이 보내고, 새 필드는 선택값이다.
- 상태 API는 집계값만 공개한다(호스트·IP·DB 정보 제외).

**설계 메모 (실제 장애는 아님)**
- Jackson은 `isX()`·`getX()` 형태 메서드를 JSON 속성으로 내보낸다. 그래서 `Message`의 보조 판별 메서드를 `table()`로 이름 지어 응답에 섞이지 않게 했다. 소켓 테스트에서 응답에 `table` 필드가 없음을 확인한다.

```

**증상**: 이름표·문 이름·배너의 한글 획이 끊김.

**원인 (실측 564 CSS px × DPR 1.25 = 705 기기 픽셀)**
1. 800×600 캔버스를 CSS로 705px까지 축소하면서 `image-rendering: pixelated`(최근접)가 픽셀 줄의 약 12%를 버렸다.
2. `pixelArt: true`이면 글자 텍스처도 최근접 필터를 써서 같은 손실이 한 번 더 생겼다.
3. `monospace`·`Arial`에는 한글 글리프가 없어 대체 글꼴로 그려졌고, 9~10px로 너무 작았다.

**해결**
| 파일 | 내용 |
|---|---|
| `frontend/src/game/render/renderScale.ts` | `renderZoomFor()`(표시 너비×DPR/800, 0.5~3), `canvasSizeFor()`, `crispText()`(해상도 = 렌더 배율), `applyRenderZoom()`(카메라 줌 + 컨테이너 안 글자 갱신), `UI_FONT`·`MONO_FONT` |
| `frontend/src/components/GameCanvas.tsx` | 표시 크기로 게임 생성, `ResizeObserver`로 `game.scale.resize` |
| `LobbyMultiplayer.ts`, `RemotePlayer.ts`, `ChatBubble.ts`, `DoorAnimator.ts`, `RoomFx.ts` | 모든 캔버스 글자를 `crispText`로 |

**기술 포인트**: **세계 좌표 800×600은 고정**(서버 충돌과 공유)하고, 렌더 해상도만 기기 픽셀에 맞춰 카메라 줌으로 확대·축소한다. 결과적으로 브라우저 재샘플링이 0이 된다(측정 0.998:1).

관련 문서: `docs/room-atmosphere.md` "글자 렌더링"

## 4. 고지연 네트워크 대응 (PR #23)

---
title: 슬개기술연구소 — 1초 왕복 네트워크에서 끊기지 않는 멀티플레이어 만들기
date: 2026-11-16
createdAt: 2026-11-16T22:04:39+09:00
tags: WebSocket, Spring Boot, nginx, Vite, Network
summary: 운영 경로의 지연을 브라우저와 curl로 측정하고, 압축·캐시·청크 분리와 시간 제한 완화로 대응한 커밋을 코드와 작업 문서로 정리했다.
category: seulgae-tech-lab
---
```

**증상**: 방 이동 중 연결 끊김, 전체적인 버퍼링.

**진단 (운영 사이트를 브라우저 F12와 curl로 측정)**
- nginx가 직접 주는 정적 파일도 API와 똑같이 왕복 0.6~1.6초 → 백엔드가 아니라 **Tailscale Funnel 중계 경로** 지연.
- TCP 45ms인데 **TLS 4.7초**, WebSocket welcome까지 3~5초.
- JS 1.5MB를 **압축 없이**, 캐시 헤더 없이 전송해 첫 로드가 16.7초였다.
- 렌더링은 60fps로 원인이 아니었다. 프로토콜 수준 재현(테스트 소켓으로 문까지 걸어가 방 이동 왕복)에서는 끊김 없음.

**해결**
| 파일 | 내용 |
|---|---|
| `deploy/nginx.conf` | gzip, `/assets/` 1년 `immutable`, HTML `no-cache` |
| `.github/workflows/ci.yml` | 프런트 이미지를 띄워 `nginx -t`·gzip·캐시 헤더 검사 |
| `frontend/vite.config.ts` | Phaser·React 벤더 청크 분리(재배포 시 앱 30KB만 다시 받음) |
| `frontend/src/features/multiplayer/MultiplayerClient.ts` | 방 이동 응답 제한 5→15초, 업로드 대기열 4→16KB |
| `frontend/src/features/multiplayer/model/protocol.ts` | `closeCause()`: 종료 코드를 사람이 읽는 원인으로 바꿔 콘솔에 기록 |
| `backend/.../LobbySocketHandler.java` | 송신 제한 1→5초, 버퍼 128KB, 제어 대기열 16→64 |

**트러블슈팅**
- 테스트에서 `4500` 종료 로그가 간헐적으로 보였다. 이전 커밋과 반복 비교(전 0/0/0/0, 후 0/3/4)한 결과, 테스트 종료 시 이미 닫히는 소켓에 퇴장 알림을 보내다 실패한 **teardown 경쟁**이었다. 실제 연결에는 영향이 없다.

관련 문서: `docs/network-latency.md`

- **의자 선택 규칙**: 의자는 책상을 바라보므로 "의자 뒤(아래)에서 접근할 때만" 앉기 대상이다. 가장자리 거리가 가장 가까운 대상을 고른다. 회의실 의자에 앉으면 테이블 대화가 자동으로 켜진다(테이블 범위 64→96px).
- 낙관적 UI: 먼저 앉은 모습을 보여 주고, 1.5초 안에 서버 `seat`이 확인되지 않으면 일어난다.

**트러블슈팅**
- 의자 테스트 실패: 구형 입력 모드는 마지막 방향을 300ms 유지해서, 다른 사람이 걷는 사이 앉은 사람이 "이동"으로 처리됐다. 테스트에서 정지 입력을 보내도록 수정했다.
- CI `operations` 실패: 기존 사전 점검 테스트가 "V2는 거부"라는 옛 규칙을 고정하고 있었다. V0·V3만 거부하도록 수정했다(`ec13d82`).
- 배포 실패 `DB schema 1 outside compatible range 2..2`: 새 릴리스가 V2를 요구하는데 운영 DB가 V1이었다. `migrate-prod.py` 실행 후 해결(설계된 안전장치).
- 일반 작성 API는 개발 전용으로 유지하고, 공개 쓰기는 일지·안건 전용 엔드포인트로만 열었다.

## 10. 배포가 서버 저장소를 릴리스 커밋으로 맞추기 (PR #32)

**블로그 front matter 초안** (Codex가 그대로 쓰거나 다듬는다)
```yaml
---
title: 슬개기술연구소 — 이미지는 최신인데 설정은 옛날? 자동 배포의 숨은 틈
date: 2026-11-17
createdAt: 2026-11-17T16:00:00+09:00
tags: CI/CD, Docker Compose, GitHub Actions, Python, DevOps
summary: 카카오 로그인 설정이 운영에 반영되지 않은 원인을 추적했다. 자동 배포가 이미지만 새로 받고 서버 저장소의 Compose 파일은 갱신하지 않았다. 배포 스크립트가 서버 저장소를 릴리스 커밋으로 맞추고 자기 자신을 다시 실행하도록 고쳤다.
category: seulgae-tech-lab
---
```
> createdAt은 대략 시각이다. 실제 시각은 `git log`로 확인한다.

**증상**: 카카오 로그인 PR(#30)이 머지·자동 배포됐는데 운영 화면에 로그인 버튼이 없었다. `/api/auth/me`가 `kakaoEnabled: false`였다.

**원인 추적**
- 백엔드 이미지는 최신 커밋이었다.
- 그런데 컨테이너에는 `LAB_AUTH_*` 환경변수도, 비밀 파일 두 개도 없었다.
- 컨테이너의 Compose 라벨이 가리키는 서버 저장소는 두 PR 전 커밋에 머물러 있었다.
- CI 배포는 서버에서 `./deploy.sh`만 실행한다. 이미지는 릴리스 manifest로 고르지만, Compose 파일과 `ops.py`는 서버 저장소의 옛 파일을 그대로 썼다. 사전 점검도 옛 코드라 새 비밀 파일 검사를 하지 않았다.

**긴급 조치**
- 서버 저장소를 main으로 맞췄다.
- `./deploy.sh`는 "이미지가 같다"며 아무것도 하지 않아서 `./start.sh`(같은 이미지로 `compose up -d`)를 썼다. 백엔드만 재생성되었다.
- 결과: `kakaoEnabled: true`.

**구현**
- `sync_checkout(candidate)`의 순서:
  1. `git fetch` 후 릴리스 SHA가 origin/main의 조상인지 확인한다.
  2. HEAD가 다르면 추적 파일 변경이 없는지 확인한다.
  3. `git checkout --detach <SHA>`로 옮긴다.
- 옮겼다면 `os.execv`로 **릴리스 커밋의 ops.py**를 다시 실행한다. 사전 점검부터 새 코드로 돈다. `STLAB_DEPLOY_SYNCED` 환경변수로 무한 반복을 막는다.
- 이미지가 같을 때도 `activate`(`compose up -d --wait`)를 다시 적용한다. 설정만 바뀐 배포도 반영된다.

**주요 소스**
| 파일 | 내용 |
|---|---|
| `deploy/ops.py` | `sync_checkout`, 사전 점검 전 재실행, 같은 이미지일 때 설정 재적용 |
| `deploy/test_ops.py` | 이미 최신·옮기기·로컬 변경·조상 아님·재실행·재실행 후 중복 동기화 없음 |
| `docs/operations.md` | 서버 저장소 detached HEAD 운영 방식 |

**기술 포인트**
- **execv와 파일 잠금**: Python이 여는 파일은 기본적으로 상속되지 않는다(close-on-exec). 그래서 `execv`로 바꿔 실행하면 `flock` 잠금이 자동으로 풀린다. 새 프로세스가 같은 잠금을 다시 잡는다.
- **detached HEAD**: 서버 저장소를 브랜치가 아니라 정확한 릴리스 SHA에 고정한다. main이 릴리스보다 앞서 있어도(CI 진행 중) 이미지와 설정이 어긋나지 않는다.

**트러블슈팅**
- **로컬에 Python이 없음**: Windows의 `python`은 스토어 안내 스텁이고, `ops.py`는 Linux 전용 `fcntl`을 쓴다.
  - 해결: 테스트 파일만 서버의 임시 폴더에 복사해 `python3 -m unittest`로 실행한 뒤 지웠다.
- **최초 1회는 수동**: 이 PR이 머지된 직후 자동 배포는 아직 옛 `ops.py`로 돈다. 그래서 머지 후 서버 저장소를 한 번 직접 main으로 맞춰야 이후부터 자동으로 맞춰진다.

관련 문서: `docs/operations.md`

## 12. 한 IP에 한 명만: 같은 주소의 새 창이 기존 연결을 대신하기 (PR #34)

**블로그 front matter 초안** (Codex가 그대로 쓰거나 다듬는다)
```yaml
---
title: 슬개기술연구소 — 새 창을 열 때마다 연구원이 늘어나는 문제와 1주소 1연결
date: 2026-11-17
createdAt: 2026-11-17T12:45:00+09:00

summary: 같은 사람이 새 창을 열면 로비 인원이 늘어나던 문제를 같은 IP의 새 연결이 기존 연결을 대신하는 방식으로 막았다. 프록시 체인에서 믿을 수 있는 방문자 주소를 먼저 확인하고, 두 창이 서로 끊어 내는 재연결 루프도 막았다.
category: seulgae-tech-lab
---
```
> createdAt은 대략 시각이다. 실제 시각은 `git log`로 확인한다.

**구현**
- 핸드셰이크 때 방문자 주소를 연결 속성에 남긴다. 운영 설정(`LAB_MULTIPLAYER_SINGLE_CONNECTION_PER_ADDRESS=true`)에서는 같은 주소의 기존 연결을 종료 코드 4409로 끊고, 그다음에 입장시킨다. 기존 연결을 입장 전에 정리하므로 정원 계산에서도 빠진다.
- 클라이언트는 4409를 받으면 다시 연결하지 않는다. 대신 "다른 창에서 접속해 이 창의 연결을 끊었어요. 새로고침하면 이 창으로 다시 접속해요."를 보여 준다. 다시 연결하면 두 창이 번갈아 서로를 끊는 루프가 생기기 때문이다.
- 쓰기 제한(`WriteRateLimiter`)과 같은 주소 판단을 쓰도록 `ClientAddress`로 분리했다.
- nginx의 `/ws/lobby` 경로에도 `X-Forwarded-For`를 넘기게 했다. 원래 `/api/`에만 있었다.
- 로컬 개발·테스트는 모든 창이 127.0.0.1이라 기본값은 꺼짐이다.

**주요 소스**
| 파일 | 내용 |
|---|---|
| `backend/.../common/web/ClientAddress.java` | X-Forwarded-For 첫 주소, 없으면 직접 연결 주소 |
| `backend/.../multiplayer/lobby/config/LobbyWebSocketConfig.java` | 핸드셰이크에서 방문자 주소를 속성에 저장 |
| `backend/.../multiplayer/lobby/websocket/LobbySocketHandler.java` | `REPLACED`(4409), 같은 주소의 기존 연결 정리 |
| `frontend/src/features/multiplayer/{MultiplayerClient.ts,model/protocol.ts}` | `replaced` 상태, 재연결 중단 |
| `compose.yml`, `deploy/nginx.conf` | 운영에서 켜기, WebSocket 경로 주소 전달 |
| `backend/.../LobbySingleConnectionTest.java`, `frontend/tests/multiplayer.test.mjs`, `deploy/test_compose.py` | 실제 소켓 대체·인원·다른 주소 유지, 재연결 안 함, 운영 설정 |

**기술 포인트**
- **믿을 수 있는 주소인가**: X-Forwarded-For의 첫 값은 보통 클라이언트가 위조할 수 있다. 위조할 수 있다면 남의 IP를 적어 그 사람의 연결을 끊는 공격이 된다.
  - 확인 방법: 위조한 헤더(문서용 주소 203.0.113.9)를 붙여 운영에 요청했다. nginx 로그에는 실제 주소만 남았다. Funnel이 이 헤더를 실제 방문자 주소로 새로 쓴다는 뜻이다.
  - 백엔드 포트는 외부에 열려 있지 않아 nginx를 거치지 않는 요청은 없다.
- **같은 공유기 사용자**: 집·회사처럼 같은 공인 IP를 쓰는 서로 다른 사람도 한 명으로 취급된다. 의도한 제한의 부작용으로 받아들였다.

**트러블슈팅**
- **스택 PR이 main에 안 들어감**: #33을 #32 위에 쌓아 베이스를 #32 브랜치로 두었다. 그런데 #32가 먼저 main에 머지된 뒤 #33이 그 브랜치로 머지되어 main에 반영되지 않았다(첫 커밋만 들어감).
  - 해결: 의자 2초 안내 커밋을 main 기준 새 브랜치로 옮겨 이번 PR에 함께 넣었다. 이후로는 PR을 쌓지 않고 main 기준으로 만든다.

  - 값이 없거나 불리언이 아니면 400, 없는 기록은 404.
  - 내용·수정 시각은 바꾸지 않는다.
- CI 릴리스 `db_schema` **4..4**: 운영 DB가 V4로 올라간 뒤에 머지해야 한다.

**기술 포인트**
- **보이는 만큼만 보내기**: 모든 참가자에게 모든 방을 보내지 않는다. 관제실 참가자에게만, 4틱(약 5Hz)마다 방별 목록을 붙인다. 클라이언트는 알려진 방, 정원(5) 이하, 중복 없는 참가자만 받아들인다.
- **데이터로 정하는 방 기능**: "관제실인가"를 방 id로 하드코딩하지 않고, 공유 맵에 `cctv` 상호작용이 있는 방으로 판단한다.
- **텍스처 크기 규칙**: 기존 테스트는 방 테마의 교체 텍스처가 원래 가구와 같은 크기여야 한다고 검사한다. 모니터 월·나무처럼 크기가 다른 가구는 교체(alias)하지 않고, 공유 맵에 전용 텍스처 키를 직접 썼다. 호수·강은 텍스처가 없으면 그리지 않고, 충돌만 남긴 채 연출이 직접 그린다.
- **시간대 층 다시 그리기**: 하늘·물·빛·생물은 한 "층"으로 묶어 1분마다 시간대가 바뀌었는지 확인한다. 바뀌면 층만 지우고 다시 그린다.

**트러블슈팅**
- **브라우저 확인 도구에서 E 키가 안 먹음**: 도구의 글자 키 입력은 `keyCode`가 비어서, keyCode로 키를 구분하는 Phaser가 무시했다. 방향키는 됐다.
  - 해결: 모바일 크기로 바꿔 화면의 E 버튼(React onClick → 같은 상호작용 이벤트)과 조이스틱(PointerEvent)으로 확인했다.
- **숨겨진 창에서 애니메이션이 느림**: 미리보기 창이 가려지면 초당 2프레임으로 줄어, 트윈(찌 던지기)이 실제 시간보다 늦게 끝났다. 시간 기반 타이머(입질)와 어긋나서 입질 타이밍 맞추기 확인이 어려웠다.
  - 결론: 실제 브라우저(60fps)에서는 문제없다. 던지기·대기·입질·게이지·놓침까지 화면으로 확인했고, 잡기·기록은 단위 테스트로 검증했다.
- **다리·데크 위의 캐릭터가 밑에 그려짐**: 다리·데크를 아래 끝 y를 깊이로 그려서, 그보다 위(y가 작은)에 선 캐릭터가 판자 밑으로 들어갔다.
  - 해결: 걸어 다니는 바닥이므로 물(-44~-42) 바로 위인 고정 깊이 -41(\`WALKABLE_DECK_DEPTH\`)로 그려 모든 캐릭터 아래에 두었다.
- **기존 테스트 갱신**: 로비 의자를 치워 의자 테스트를 관제실 의자로 옮겼다. 개발 연구실 문이 옆으로 가서 문 테스트도 "나가기"로 바꿨다.

**구현** (자세한 내용은 `docs/sound.md`)
- **합성 음원**: 외부 음원 대신 `synth.ts`가 22,050Hz 모노로 직접 만든다.
  - 배경음악 6곡: 일렉트릭 피아노·벨 배음, 카플러스-스트롱 기타, 부드러운 드럼, 레코드 잡음, 짧은 잔향.
  - 환경음 7종과 효과음 29종.
  - 저장소에 오디오 파일이 0개라 다운로드 용량도 없다. 곡 하나 합성에 약 60~210ms, 효과음 전체는 23ms다.
- **AudioManager**: 게임마다 하나.
  - 합성 결과를 `AudioBuffer`로 바꿔 Phaser 오디오 캐시에 한 번만 넣는다.
  - 방을 옮기면 음악·환경음을 교차 페이드한다. 같은 곡이면 이어서 재생한다.
  - 효과음 동시 재생은 8개(원격 발걸음 4개)로 제한한다.
  - 설정을 바꾸면 재생 중인 소리에 바로 반영한다.
- **발걸음**: 실제 좌표 이동 거리로만 판정하고, 바닥 재질별로 소리를 고른다. 다른 연구원 발걸음은 보간된 위치를 기준으로 거리 감쇠·좌우 위치를 준다.
- **연결**: 문, 방 전환, 의자, 패널(장비별 소리), 식물, 커피·케이크, 책장, 안내 방송, CI 성공·실패, 서버 경보, 관제실 점검음, 채팅 알림, 낚시.
- **설정 창**: 게임 화면 오른쪽 위.
  - 전체 80·음악 30·효과 60·환경 40% 기본값, 음소거, 카테고리 켜기, 초기화.
  - localStorage에 저장한다.

**기술 포인트**
- **Phaser 캐시에 직접 만든 버퍼 넣기**: `WebAudioSound`는 `game.cache.audio.get(key)`의 AudioBuffer로 재생한다. 그래서 `cache.audio.add(key, buffer)`만 하면 파일 로드 없이 `game.sound.add(key)`가 그대로 동작한다.
- **끊김 없는 반복**: 음악은 루프 길이를 넘어 울리는 꼬리를 처음에 더한다. 잡음 환경음은 끝 0.5초를 처음과 교차한다.
- **테스트 가능한 설계**: AudioManager는 Phaser 타입 대신 쓰는 메서드만 구조적으로 받는다. 그래서 node 테스트에서 가짜 사운드 매니저와 수동 타이머로 페이드·중복 방지·동시 재생 제한을 검증했다.

**트러블슈팅**
- **실제 소리를 귀로 확인할 수 없음**: 개발 서버 전용 `__labAudio.debug()`로 Chrome(앱 내장 브라우저)에서 확인한 것:
  - AudioContext가 running이다.
  - 로비 음악(볼륨 0.24 = 80%×30%)·환경음이 재생 중이다.
  - 바깥으로 나가면 곡이 바뀐다.
  - 음소거·볼륨을 바꾸면 바로 반영되고 localStorage에 저장된다.

**1. 의자에 앉으면 2초 뒤 일어나는 버그(운영)**
- **원인**: 걸어오다 바로 E를 누르면 두 가지 순서 문제가 생긴다.
  - 클라이언트: 걸음(이동 명령)은 50ms마다 묶어 보내고 앉기 요청은 즉시 보낸다. 그래서 E 직전 걸음이 앉기 뒤에 도착했다.
  - 서버: 이동 명령을 시간 예산에 맞춰 대기열에서 처리한다. 앉기 처리 뒤에 앉기 전의 걸음이 처리되면서 "움직였다"며 자리에서 일으켰다.
  - 클라이언트는 1.5초 안에 서버의 앉음 확인을 못 받으면 일어나게 되어 있다. 운영 왕복이 약 1초라 2초쯤 뒤에 일어났다. 로컬은 지연이 거의 없어 재현되지 않았다.
- **해결**
  - 클라이언트: 앉기 요청 전에 남은 걸음을 모두 먼저 보낸다.
  - 서버: 앉기 요청 시점까지 받은 이동 번호(`seatAfter`)를 기억한다. 그 번호 이하의 걸음은 자리에서 일으키지 않는다. 그런 걸음이 대기열에 남아 있으면 다 처리한 위치에서 앉는다(`seatRequest`). 앉은 뒤에 보낸 걸음만 일으킨다.
  - 서버 확인 대기 시간을 3초(`SEAT_CONFIRM_MS`)로 늘렸다.

**2. 모바일 카카오 로그인 후 머리 위 이름이 "연구원"으로 남는 버그**
- **원인**: 게임은 로그인 확인을 최대 2.5초만 기다리고 시작한다. 모바일처럼 확인이 늦으면 임시 이름 "연구원-xxxx"로 접속한 뒤 다시 바꾸지 않았다.
- **해결**: 로그인 확인이 늦게 끝나면 회원 닉네임으로 바로 다시 접속한다(`applyNickname`, 종료 코드 4006).
  - 같은 이름은 한 번만 시도한다. 서버가 중복 이름을 "이름-xxxx"로 바꿔 줘도 다시 접속을 반복하지 않는다.

**3. 회의실 세로 원목 테이블**
- 가로 테이블을 세로로 긴 원목 테이블로 바꿨다(새 텍스처: 나뭇결, 서류, 커피잔, 작은 화분).

- 스폰이 테이블 대화 범위 안에 들지 않게 테이블을 조금 올렸다. 테이블 대화 범위는 48, 스폰은 y 480이다.
- 의자는 기존 텍스처(뒷모습)를 그대로 써서, 옆을 보고 앉는 모습은 아니다(다음 작업 거리).

## 20. 스키마 V5 확장: 공통코드와 업무 게시판 테이블 (PR #42, 확장 단계)

  - `lab.coin_events`: 동전 변동 기록, 하루 보상 한도 계산.
  - `lab.items`: 아이템. 주인이 없으면 방 바닥에 놓인 상태다.
  - 공통코드 ITEM_KIND, COIN_REASON.
- 도구: `migrate-prod.py` 최신 V5, `ops.py` 지원 V1~V5, CI 릴리스 `db_schema` 4..5, 배포 테스트 갱신, 운영 문서 V5 절차.

**기술 포인트**
- **공통코드 복합 외래키**: `category_group` 열을 CHECK로 'WORK_CATEGORY'에 고정한다. 그다음 (category_group, category)를 공통코드 (code_group, code)에 외래키로 걸어, 다른 그룹의 코드가 섞여 들어가지 못하게 했다.
- **확장 먼저**: 새 테이블만 만들고 앱 코드는 아직 쓰지 않는다. 그래서 운영 DB가 V4여도 배포된다.

**확인**: 배포 테스트 49개 통과(서버 임시 폴더). SQL의 Flyway 적용은 CI(PostgreSQL 18)에서 확인한다.

## 25. 게시판·방명록 입력에서 띄어쓰기가 안 되던 버그 (PR #47)

> 24번(방명록)의 후속 수정이다. 짧은 트러블슈팅 글로 쓰기 좋다.

**증상**: 사무실 업무 게시판, 로비 방명록 같은 창에서 글을 쓸 때 스페이스바를 눌러도 띄어쓰기가 들어가지 않았다. 한글은 잘 입력됐다.

**원인**
- Phaser는 `addKey`·`createCursorKeys`로 등록한 키(방향키, Space, Shift, W/A/S/D, E, I)를 "가로채기(capture)" 목록에 넣는다.
- 그 키의 keydown은 **창(window) 전체**에서 `preventDefault`된다. 포커스가 입력 칸에 있어도 마찬가지다.
- 한글은 IME 조합 중에 keyCode 229로 들어와 가로채기를 피한다. 그래서 한글은 써지고 띄어쓰기(keyCode 32)만 막혔다. 영문 w·a·s·d·e·i도 같은 이유로 막혔다.
- 채팅창과 연구 아이디어 입력폼은 keydown 전파를 막고 있어서(`stopPropagation`) 문제가 없었다. 업무 게시판과 방명록 창에는 그 처리가 없었다.

**해결**
- 게임 장면이 입력 칸 포커스를 보고 가로채기를 켜고 끈다.
  - 입력 칸에 포커스가 있으면 `keyboard.disableGlobalCapture()`, 벗어나면 `enableGlobalCapture()`.
  - `focusin`·`focusout` 이벤트로 즉시 반영하고, 매 프레임 update에서도 한 번 더 맞춘다.
  - 장면이 끝나면 원래대로 켠다.
- 창마다 `stopPropagation`을 붙이는 대신 한 곳에서 처리했다. 앞으로 새 입력 창을 만들어도 같은 문제가 생기지 않는다.
- 게임 중에는 여전히 Space·방향키를 가로챈다. 페이지가 스크롤되지 않는다.

**주요 소스**
| 파일 | 내용 |
|---|---|
| `frontend/src/game/scenes/LabLobbyScene.ts` | 입력 칸 포커스에 따라 키 가로채기 끄고 켜기 |
| `frontend/tests/interaction.test.mjs` | 포커스 전환·장면 종료 시 가로채기 상태 테스트 |

**확인**
- 프론트 테스트 113개, 타입 검사 통과.
- DB 없는 로컬 실행에서 브라우저에 Space keydown을 보내 `defaultPrevented`를 비교했다.
  - 수정 전: 일반 입력 칸에서 `true`(막힘).
  - 수정 후: 입력 칸 Space·w 모두 `false`(입력됨). 게임 화면(본문)에서는 `true`(계속 가로챔). 입력 칸을 벗어나면 다시 `true`.

**기술 포인트**
- **한 번의 UPDATE로 범위 지키기**
  - 회복: `SET hp = LEAST(hp_max, hp + :n)`
  - 차감: `WHERE hp + :n >= 0`
  - 동시에 여러 요청이 와도 0 밑이나 최대치 위로 가지 않는다. DB CHECK도 한 번 더 막는다.
- **실패하면 아무것도 바꾸지 않기**: 오락실은 "기력 확인 → 동전 → 기력 차감"을 한 트랜잭션으로 묶었다. 중간에 실패하면 동전도 되돌린다.
- **상태 코드로 이유 구분**: 409 동전 부족, 422 이미 가득, 423 기운 부족. 응답 본문 없이도 화면이 알맞은 안내를 고른다.
- **변화량은 서버 값에서 계산**: 케이크로 +10을 사도, 47에서 최대 50이면 화면에는 "+3"이 뜬다.

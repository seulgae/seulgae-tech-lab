```yaml
---
title: 슬개기술연구소 — 방마다 다른 상호작용, 서버 상태와 테이블 대화
date: 2026-11-16
createdAt: 2026-11-16T21:16:03+09:00
tags: React, Phaser, Spring Boot, WebSocket
summary: 공유 맵으로 방별 상호작용을 정의하고, 서버 상태·빌드 정보 API와 서버 좌표로 검증하는 근거리 테이블 대화를 추가한 커밋을 코드와 작업 문서로 정리했다.
category: seulgae-tech-lab
---
```

**구현**
- 공유 맵 `shared/lobby-world.json`의 방마다 `interactions`(id·kind·영역·range)를 정의했다. 서버와 클라이언트가 **같은 데이터, 같은 거리식(사각형 가장자리 거리)**으로 판정한다.
- 서버실 랙 → 실시간 서버 상태, 개발 연구실 컴퓨터 → 빌드 정보, 회의 테이블 → 근거리 "테이블 대화".

**주요 소스**
| 파일 | 내용 |
|---|---|
| `backend/.../lab/status/LabStatusController.java` | `GET /api/lab/status`(가동 시간·방별 인원·JVM 힙, `no-store`), `GET /api/lab/build`(build-info + 커밋 7자리, 16진수만 신뢰) |
| `backend/.../multiplayer/lobby/domain/LobbyWorld.java` | `Interaction.near()` 가장자리 거리 판정, `roomIds()`, `near(room, kind, x, y)` |
| `backend/.../multiplayer/lobby/domain/LobbyChat.java` | `Message.scope`(room/table), 테이블 대화는 서버 좌표 검증 + 기록 미저장 |
| `backend/.../multiplayer/lobby/websocket/LobbySocketHandler.java` | 채팅 `scope` 검증, 테이블 범위 안 참가자에게만 전달 |
| `frontend/src/game/maps/rooms.ts` | `nearestInteraction()` |
| `frontend/src/features/lab/*` | `LabInfoPanel`(3초 폴링, 응답 형식 검증), `labApi.ts`, `labTypes.ts` |
| `backend/pom.xml`, `backend/Dockerfile`, `.github/workflows/ci.yml` | `build-info` goal, `GIT_COMMIT` 빌드 인자 → `LAB_BUILD_COMMIT` |

**기술 포인트**
- 근거리 채팅은 **클라이언트가 아니라 서버 좌표**로 수신자를 정한다. 클라이언트가 조작한 위치로 엿들을 수 없다.
- 기존 클라이언트 호환: 일반 채팅은 `scope` 필드 없이 보내고, 새 필드는 선택값이다.
- 상태 API는 집계값만 공개한다(호스트·IP·DB 정보 제외).

**설계 메모 (실제 장애는 아님)**
- Jackson은 `isX()`·`getX()` 형태 메서드를 JSON 속성으로 내보낸다. 그래서 `Message`의 보조 판별 메서드를 `table()`로 이름 지어 응답에 섞이지 않게 했다. 소켓 테스트에서 응답에 `table` 필드가 없음을 확인한다.

```yaml
---
```

**증상**: 이름표·문 이름·배너의 한글 획이 끊김.

**원인 (실측 564 CSS px × DPR 1.25 = 705 기기 픽셀)**
1. 800×600 캔버스를 CSS로 705px까지 축소하면서 `image-rendering: pixelated`(최근접)가 픽셀 줄의 약 12%를 버렸다.
2. `pixelArt: true`이면 글자 텍스처도 최근접 필터를 써서 같은 손실이 한 번 더 생겼다.
3. `monospace`·`Arial`에는 한글 글리프가 없어 대체 글꼴로 그려졌고, 9~10px로 너무 작았다.

**해결**
| 파일 | 내용 |
|---|---|
| `frontend/src/game/render/renderScale.ts` | `renderZoomFor()`(표시 너비×DPR/800, 0.5~3), `canvasSizeFor()`, `crispText()`(해상도 = 렌더 배율), `applyRenderZoom()`(카메라 줌 + 컨테이너 안 글자 갱신), `UI_FONT`·`MONO_FONT` |
| `frontend/src/components/GameCanvas.tsx` | 표시 크기로 게임 생성, `ResizeObserver`로 `game.scale.resize` |
| `LobbyMultiplayer.ts`, `RemotePlayer.ts`, `ChatBubble.ts`, `DoorAnimator.ts`, `RoomFx.ts` | 모든 캔버스 글자를 `crispText`로 |

**기술 포인트**: **세계 좌표 800×600은 고정**(서버 충돌과 공유)하고, 렌더 해상도만 기기 픽셀에 맞춰 카메라 줌으로 확대·축소한다. 결과적으로 브라우저 재샘플링이 0이 된다(측정 0.998:1).

관련 문서: `docs/room-atmosphere.md` "글자 렌더링"

## 4. 고지연 네트워크 대응 (PR #23)

```yaml
---
title: 슬개기술연구소 — 1초 왕복 네트워크에서 끊기지 않는 멀티플레이어 만들기
date: 2026-11-16
createdAt: 2026-11-16T22:04:39+09:00
tags: WebSocket, Spring Boot, nginx, Vite, Network
summary: 운영 경로의 지연을 브라우저와 curl로 측정하고, 압축·캐시·청크 분리와 시간 제한 완화로 대응한 커밋을 코드와 작업 문서로 정리했다.
category: seulgae-tech-lab
---
```

**증상**: 방 이동 중 연결 끊김, 전체적인 버퍼링.

**진단 (운영 사이트를 브라우저 F12와 curl로 측정)**
- nginx가 직접 주는 정적 파일도 API와 똑같이 왕복 0.6~1.6초 → 백엔드가 아니라 **Tailscale Funnel 중계 경로** 지연.
- TCP 45ms인데 **TLS 4.7초**, WebSocket welcome까지 3~5초.
- JS 1.5MB를 **압축 없이**, 캐시 헤더 없이 전송해 첫 로드가 16.7초였다.
- 렌더링은 60fps로 원인이 아니었다. 프로토콜 수준 재현(테스트 소켓으로 문까지 걸어가 방 이동 왕복)에서는 끊김 없음.

**해결**
| 파일 | 내용 |
|---|---|
| `deploy/nginx.conf` | gzip, `/assets/` 1년 `immutable`, HTML `no-cache` |
| `.github/workflows/ci.yml` | 프런트 이미지를 띄워 `nginx -t`·gzip·캐시 헤더 검사 |
| `frontend/vite.config.ts` | Phaser·React 벤더 청크 분리(재배포 시 앱 30KB만 다시 받음) |
| `frontend/src/features/multiplayer/MultiplayerClient.ts` | 방 이동 응답 제한 5→15초, 업로드 대기열 4→16KB |
| `frontend/src/features/multiplayer/model/protocol.ts` | `closeCause()`: 종료 코드를 사람이 읽는 원인으로 바꿔 콘솔에 기록 |
| `backend/.../LobbySocketHandler.java` | 송신 제한 1→5초, 버퍼 128KB, 제어 대기열 16→64 |

**트러블슈팅**
- 테스트에서 `4500` 종료 로그가 간헐적으로 보였다. 이전 커밋과 반복 비교(전 0/0/0/0, 후 0/3/4)한 결과, 테스트 종료 시 이미 닫히는 소켓에 퇴장 알림을 보내다 실패한 **teardown 경쟁**이었다. 실제 연결에는 영향이 없다.

관련 문서: `docs/network-latency.md`

- **의자 선택 규칙**: 의자는 책상을 바라보므로 "의자 뒤(아래)에서 접근할 때만" 앉기 대상이다. 가장자리 거리가 가장 가까운 대상을 고른다. 회의실 의자에 앉으면 테이블 대화가 자동으로 켜진다(테이블 범위 64→96px).
- 낙관적 UI: 먼저 앉은 모습을 보여 주고, 1.5초 안에 서버 `seat`이 확인되지 않으면 일어난다.

**트러블슈팅**
- 의자 테스트 실패: 구형 입력 모드는 마지막 방향을 300ms 유지해서, 다른 사람이 걷는 사이 앉은 사람이 "이동"으로 처리됐다. 테스트에서 정지 입력을 보내도록 수정했다.
- CI `operations` 실패: 기존 사전 점검 테스트가 "V2는 거부"라는 옛 규칙을 고정하고 있었다. V0·V3만 거부하도록 수정했다(`ec13d82`).
- 배포 실패 `DB schema 1 outside compatible range 2..2`: 새 릴리스가 V2를 요구하는데 운영 DB가 V1이었다. `migrate-prod.py` 실행 후 해결(설계된 안전장치).
- 일반 작성 API는 개발 전용으로 유지하고, 공개 쓰기는 일지·안건 전용 엔드포인트로만 열었다.

## 10. 배포가 서버 저장소를 릴리스 커밋으로 맞추기 (PR #32)

**블로그 front matter 초안** (Codex가 그대로 쓰거나 다듬는다)
```yaml
---
title: 슬개기술연구소 — 이미지는 최신인데 설정은 옛날? 자동 배포의 숨은 틈
date: 2026-11-17
createdAt: 2026-11-17T16:00:00+09:00
tags: CI/CD, Docker Compose, GitHub Actions, Python, DevOps
summary: 카카오 로그인 설정이 운영에 반영되지 않은 원인을 추적했다. 자동 배포가 이미지만 새로 받고 서버 저장소의 Compose 파일은 갱신하지 않았다. 배포 스크립트가 서버 저장소를 릴리스 커밋으로 맞추고 자기 자신을 다시 실행하도록 고쳤다.
category: seulgae-tech-lab
---
```
> createdAt은 대략 시각이다. 실제 시각은 `git log`로 확인한다.

**증상**: 카카오 로그인 PR(#30)이 머지·자동 배포됐는데 운영 화면에 로그인 버튼이 없었다. `/api/auth/me`가 `kakaoEnabled: false`였다.

**원인 추적**
- 백엔드 이미지는 최신 커밋이었다.
- 그런데 컨테이너에는 `LAB_AUTH_*` 환경변수도, 비밀 파일 두 개도 없었다.
- 컨테이너의 Compose 라벨이 가리키는 서버 저장소는 두 PR 전 커밋에 머물러 있었다.
- CI 배포는 서버에서 `./deploy.sh`만 실행한다. 이미지는 릴리스 manifest로 고르지만, Compose 파일과 `ops.py`는 서버 저장소의 옛 파일을 그대로 썼다. 사전 점검도 옛 코드라 새 비밀 파일 검사를 하지 않았다.

**긴급 조치**
- 서버 저장소를 main으로 맞췄다.
- `./deploy.sh`는 "이미지가 같다"며 아무것도 하지 않아서 `./start.sh`(같은 이미지로 `compose up -d`)를 썼다. 백엔드만 재생성되었다.
- 결과: `kakaoEnabled: true`.

**구현**
- `sync_checkout(candidate)`의 순서:
  1. `git fetch` 후 릴리스 SHA가 origin/main의 조상인지 확인한다.
  2. HEAD가 다르면 추적 파일 변경이 없는지 확인한다.
  3. `git checkout --detach <SHA>`로 옮긴다.
- 옮겼다면 `os.execv`로 **릴리스 커밋의 ops.py**를 다시 실행한다. 사전 점검부터 새 코드로 돈다. `STLAB_DEPLOY_SYNCED` 환경변수로 무한 반복을 막는다.
- 이미지가 같을 때도 `activate`(`compose up -d --wait`)를 다시 적용한다. 설정만 바뀐 배포도 반영된다.

**주요 소스**
| 파일 | 내용 |
|---|---|
| `deploy/ops.py` | `sync_checkout`, 사전 점검 전 재실행, 같은 이미지일 때 설정 재적용 |
| `deploy/test_ops.py` | 이미 최신·옮기기·로컬 변경·조상 아님·재실행·재실행 후 중복 동기화 없음 |
| `docs/operations.md` | 서버 저장소 detached HEAD 운영 방식 |

**기술 포인트**
- **execv와 파일 잠금**: Python이 여는 파일은 기본적으로 상속되지 않는다(close-on-exec). 그래서 `execv`로 바꿔 실행하면 `flock` 잠금이 자동으로 풀린다. 새 프로세스가 같은 잠금을 다시 잡는다.
- **detached HEAD**: 서버 저장소를 브랜치가 아니라 정확한 릴리스 SHA에 고정한다. main이 릴리스보다 앞서 있어도(CI 진행 중) 이미지와 설정이 어긋나지 않는다.

**트러블슈팅**
- **로컬에 Python이 없음**: Windows의 `python`은 스토어 안내 스텁이고, `ops.py`는 Linux 전용 `fcntl`을 쓴다.
  - 해결: 테스트 파일만 서버의 임시 폴더에 복사해 `python3 -m unittest`로 실행한 뒤 지웠다.
- **최초 1회는 수동**: 이 PR이 머지된 직후 자동 배포는 아직 옛 `ops.py`로 돈다. 그래서 머지 후 서버 저장소를 한 번 직접 main으로 맞춰야 이후부터 자동으로 맞춰진다.

관련 문서: `docs/operations.md`

# Codex 블로그 작성 프롬프트

> 작성일: 2026-11-17 · 아래 "프롬프트" 블록을 그대로 Codex에 붙여 넣으면 된다.

## 프롬프트

```text
너는 이 저장소(seulgae-tech-lab)의 기술 블로그 작가다. 소스 코드는 수정하지 말고, 블로그 글 파일만 새로 만든다.

[입력]
1. docs/dev-log/README.md 와 docs/dev-log/ 의 날짜별 로그(예: 2026-11-17.md)를 먼저 읽는다.
2. 로그 각 항목의 "주요 소스" 표에 있는 파일을 직접 열어 실제 구현을 확인한다. 로그와 코드가 다르면 코드가 기준이다.
3. 필요하면 "관련 문서"(docs/*.md)와 git 이력(git log --oneline, git show <커밋>)으로 PR 번호·변경 범위를 대조한다.

[작업]
- 로그의 번호 항목 하나당 블로그 글 1편을 쓴다(예: 2026-11-17 로그 → 6편 이내, 6번 정리 작업은 짧은 글 또는 생략 가능).
- 저장 위치: docs/blog/<로그 날짜>-<영문-슬러그>.md (예: docs/blog/2026-11-17-hangul-canvas-rendering.md)
- 이미 docs/blog/에 같은 주제 글이 있으면 새로 만들지 말고 건너뛴다.

[글 구성 (한국어, 각 1,500~3,000자)]
1. 제목: 문제나 결과가 드러나게(예: "Phaser 캔버스에서 한글이 깨지던 진짜 이유")
2. 배경: 프로젝트를 한두 문장으로 소개하고 왜 이 작업이 필요했는지
3. 문제·요구사항
4. 원인 분석 또는 설계: 측정 수치와 판단 근거를 로그에서 인용
5. 구현: 핵심 코드 2~4개를 발췌(각 30줄 이하, 파일 경로 표기). 저장소에 실제로 있는 코드만 인용한다.
6. 트러블슈팅: 로그의 "트러블슈팅"을 증상 → 원인 → 해결 → 검증 순서로
7. 결과·남은 과제: 테스트 결과와 확인하지 못한 부분을 솔직하게
8. 마무리: 배운 점 3줄

[규칙]
- 운영 정보를 노출하지 않는다: 서버 IP, 호스트 이름, Tailscale/Funnel 도메인(*.ts.net), 계정·DB 사용자명, 비밀번호 파일 경로, 접속자 닉네임은 쓰지 않거나 "홈 서버", "공개 주소"처럼 일반화한다.
- 로그에 없는 성능 수치나 결과는 만들어 내지 않는다. 확인되지 않은 내용은 "확인하지 못함"으로 적는다.
- 코드 블록에는 언어 태그(java, ts, sql, nginx, yaml)를 붙인다.
- 글 맨 앞에 front matter를 둔다:
  ---
  title: "..."
  date: <로그 날짜>
  tags: [phaser, spring-boot, websocket, ...]
  summary: "한 줄 요약"
  source_prs: [#22]
  ---
- 작업을 마치면 만든 파일 목록과 각 글의 한 줄 요약을 보고한다.
```

## 참고
- 새 개발 로그가 추가되면 같은 프롬프트에서 `<로그 날짜>`만 바꿔 다시 실행한다. 이미 작성된 주제는 건너뛴다.

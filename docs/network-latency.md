# 운영 네트워크 지연 진단과 대응 (2026-11-16)

## 증상

- 방을 이동할 때 연결이 끊긴다.
- 전체적으로 버퍼링이 생긴다.

## 측정 (운영 `https://seulgae-home-server.tailac4b36.ts.net`, 개발 PC의 브라우저와 curl)

| 항목 | 값 |
|---|---|
| 정적 파일(`/favicon.svg`, nginx 직접 응답) 왕복 | 0.6~1.6초 |
| `/api/health` 왕복 | 0.8~1.4초 |
| TCP 연결 / TLS 핸드셰이크 (curl) | 45ms / **4.7초** |
| WebSocket 연결 후 welcome 수신까지 | 3~5.3초 |
| 방 이동 요청 → `room_changed` (프로토콜 재현) | 1.0~1.5초 |
| 연결된 뒤 상태 메시지 간격 | p50 49ms, p99 123ms, 서버 시계 대비 지터 p95 72ms |
| JS 번들 | 1.5MB **비압축**, `Cache-Control` 없음, 첫 로드 16.7초 |
| 렌더링 | 60fps 고정, 50ms 넘는 프레임 없음 |
| 서버 | 힙 22/323MB, 정상 |

nginx가 직접 응답하는 정적 파일도 API와 똑같이 1초 안팎이 걸린다. 따라서 지연의 원인은 백엔드가 아니라 **이 PC → Tailscale Funnel 중계 → 홈 서버** 경로다. TCP 연결은 빠른데 TLS가 4.7초 걸리는 것은, 핸드셰이크의 왕복이 매번 중계를 거치기 때문이다. 한번 연결된 WebSocket 스트림은 고르게 도착한다.

진단 중 같은 시간대에 다른 접속(사용자의 다른 브라우저로 보임)이 퇴장과 재입장을 반복하는 것이 관찰됐다. 반면 진단에 쓴 탭에서는 25초 연속 이동과 방 이동 여러 번 동안 끊김이 재현되지 않았다. 끊긴 쪽 기기의 종료 코드는 확인하지 못했다.

## 원인 분석

왕복이 약 1초이고 연결 수립이 수 초씩 걸리는 경로에서, 기존 한도 몇 개가 정상 지연까지 끊김으로 처리할 수 있었다.

| 한도 | 기존 | 위험 |
|---|---|---|
| 클라이언트 방 이동 응답 대기 (`4005`) | 5초 | 왕복 1초에 정체가 겹치면 정상 응답 전에 스스로 끊음 |
| 클라이언트 업로드 대기열 (`4003`) | 4KB(약 1초 분량 입력) | 업로드가 잠깐 막히면 스스로 끊음 |
| 서버 단일 송신 시간 (`4500`) | 1초 | 기록·스냅샷이 몰리는 방 이동 직후에 넘기 쉬움 |
| 서버 제어 메시지 대기열 (`4500`) | 16개 | 방 이동 때 승인·기록·입퇴장 알림이 한꺼번에 쌓임 |

버퍼링 체감은 주로 첫 로드(비압축 1.5MB × 약 90KB/s)와, 요청마다 붙는 1초 왕복에서 온다. 렌더링은 원인이 아니다.

## 조치 (이 저장소)

- **nginx**:
  - JS·CSS·JSON·SVG를 gzip으로 압축한다(1.5MB → 약 420KB).
  - 해시가 붙은 `/assets/`는 `Cache-Control: public, max-age=31536000, immutable`, 진입 HTML은 `no-cache`로 둔다.
  - CI에서 프런트엔드 이미지를 띄워 `nginx -t`, gzip, 캐시 헤더를 확인한다.
- **번들**: Phaser(gzip 318KB)와 React(68KB)를 별도 청크로 나눴다. 재배포 때는 앱 코드(gzip 약 30KB)만 새로 받는다.
- **클라이언트** (`MultiplayerClient`):
  - 방 이동 응답 제한을 15초(`ROOM_RESPONSE_TIMEOUT_MS`)로 늘렸다.
  - 업로드 대기열 한도를 16KB(`INPUT_BACKPRESSURE_BYTES`, 약 4초 분량)로 늘렸다.
  - 연결이 끊기면 콘솔 `[multiplayer] 연결 종료`에 `cause`(사람이 읽는 원인)와 `travelling`(방 이동 중이었는지)을 함께 남긴다.
- **서버** (`LobbySocketHandler`):
  - 단일 송신 제한을 5초(`SEND_TIME_LIMIT_MS`)로 늘렸다.
  - 송신 버퍼를 128KB, 제어 메시지 대기열을 64개로 늘렸다.
  - 이동 상태는 원래대로 최신 1건만 남기므로, 느린 연결은 갱신 빈도만 줄어든다.
- 이동 검증(시간 예산, 백로그 2초, 입력 빈도)과 방 이동 검증·쿨다운은 바꾸지 않았다.

## 운영자 확인 권장 (인프라, 이 저장소 밖)

- 끊김이 다시 생기면 그 기기의 F12 콘솔에서 `[multiplayer] 연결 종료`의 `code`·`cause`를 확인한다. 서버 쪽은 `./logs.sh`의 `Lobby connection closed: code=…, reason=…`를 함께 보면 원인이 확정된다.
- Funnel은 공개 인터넷용 중계 경로다. 접속하는 기기가 같은 tailnet에 있다면 `tailscale serve`(tailnet 전용 HTTPS)나 직접 연결을 쓰면 왕복이 크게 준다. `tailscale status`·`tailscale ping seulgae-home-server`로 경로가 `relay`인지 `direct`인지 확인할 수 있다.

## 검증

- 백엔드 테스트 전체 통과. 추가한 테스트: 2초 걸리는 송신은 연결을 유지하고, 5초 넘게 멈춘 송신은 정리한다(`LobbySocketCloseTest`).
- 프런트엔드 58/58 통과. 추가한 테스트(`latency-tolerance.test.mjs`): 6초 늦은 방 이동 응답에도 끊지 않고 15초를 넘으면 4005로 복구한다, 8KB 대기열에서도 입력을 계속 보낸다, 종료 원인을 설명한다.
- 빌드 결과: phaser 318KB / react 68KB / 앱 30KB (gzip).
- 운영 반영 후의 실제 끊김 감소는 사용자가 확인한다.

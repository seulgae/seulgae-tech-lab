# 16단계 이동 진동 수정 기록

## 확인한 원인

로컬 위치를 쓰는 경로를 조사했다. `Player.update()`는 속도만 설정하고 Arcade Physics가 프레임별 이동과 충돌을 처리한다. 문제 경로는 `LobbyMultiplayer.applySnapshot()`이었다. 서버 수신 콜백에서 지연된 서버 위치를 현재 Sprite 위치와 직접 비교해 `body.reset()`으로 덮어썼다. React 상태 갱신이나 원격 캐릭터 보간은 로컬 좌표를 쓰지 않았다.

Phaser **3.90.0**의 실제 `Body`로 다음을 재현했다. 현재 캐릭터의 발밑 Body는 20×16이고 Sprite origin은 (0.5, 1), scale은 2다.

- Sprite (400,400)의 정상 Body 좌상단은 (390,384).
- `body.reset(390,400)`은 속도를 (0,0)으로 만들고 `blocked`를 초기화한다.
- reset 직후 Body 좌상단은 Sprite 전체 외형 기준 (374,352).
- 다음 물리 preUpdate가 발밑 offset을 다시 적용하면 (380,384)가 된다. 기대한 발밑 기준에서 X 6px, Y 32px 불일치가 생겼다.

따라서 단순한 보정 계수 문제만이 아니었다. 서로 다른 시점의 위치를 비교하는 오차와, 네트워크 콜백 도중 속도·충돌 상태·Body 기준점을 초기화하는 경로를 함께 제거했다. 이는 로컬 코드 및 실제 Phaser Body로 확인한 원인이다. 운영 브라우저의 기존 FPS나 프레임 추적을 확보한 것은 아니다.

## 변경한 구조

- `MultiplayerClient`는 실제 이동 입력 전송 시 `seq`만 로컬 콜백에 알려준다. 좌표를 서버에 보내지 않는다.
- `LocalReconciliation`은 해당 입력을 전송했을 때의 예측 위치를 최대 256개 저장한다. 서버 `ack`의 과거 위치와 서버 좌표를 비교해, 이미 진행한 미확인 로컬 이동을 보존한다. 서버는 기존대로 자신의 시계로 적분하므로 완전한 결정론적 입력 재생은 도입하지 않았다.
- 이동 중 16px 이하는 서버 50ms 틱 이동과 렌더링 차이로 허용한다. 정지 중 잔여 오차 허용치는 2px이다. 같은 이동 ack나 오래된 ack는 중복 보정하지 않는다.
- 수신 콜백은 오차만 기록한다. Arcade Physics의 `postUpdate`가 끝난 뒤 Scene `POST_UPDATE`에서 한 번만 위치를 보정한다.
- 일반 보정은 지수적으로 줄이되 최대 60px/초로 제한한다. Sprite와 Body의 현재·이전 프레임 위치를 같은 양만큼 옮겨 속도, 충돌 플래그, 발밑 offset을 유지한다. `body.reset()`을 사용하지 않는다.
- 일반 보정 경로는 공유 맵의 벽·가구·월드 경계를 축별로 검사한다. 재접속과 128px 초과의 큰 **ack 기준** 오차는 서버가 검증한 위치로 한 번 재동기화한다. 대응 기록이 없으면 즉시 현재 좌표를 덮어쓰지 않고, 1초 이상 기록이 없으면서 큰 오차가 남을 때만 재동기화한다.
- 장면 종료 시 POST_UPDATE 리스너와 예측 기록을 정리한다. 원격 캐릭터의 기존 보간, 애니메이션, 입퇴장 처리는 유지한다.

서버 코드·프로토콜·Rate Limit·속도·맵 충돌·sequence 검증을 변경하지 않았다. DB, 배포 설정, 인프라도 변경하지 않았다.

## 정량 재현 및 결과

첫 비교는 **실제 Phaser Body를 사용한 60Hz 고정 스텝의 격리된 자동 테스트**다. 네 방향과 네 대각선 각각 1초 동안 200px/초로 이동하고 서버 스냅샷에 150ms 지연을 적용했다. 이 격리 테스트에는 가구 충돌을 넣지 않았으며, 충돌은 별도 경계 테스트와 브라우저에서 확인했다.

| 항목 | 기존 알고리즘 | 수정 알고리즘 |
| --- | ---: | ---: |
| 입력 방향과 반대로 움직인 프레임 / 각 방향 | 1 | 0 |
| 불필요한 보정 / 각 방향 | 1 | 0 |
| 보정 이동 거리 / 각 방향 | 6.67px | 0px |
| 1초 이동 거리 / 각 방향 | 190px | 200px |

그다음 **실제 로컬 Tomcat + Vite + 브라우저 2개** 사이에 테스트 전용 TCP 중계기를 두어 각 방향 75ms, 추가 RTT 150ms를 적용했다. 키를 누른 시간을 합쳐 120초 동안 WASD, 방향키, 네 대각선, 빠른 방향 전환을 실행했다. 같은 연결은 약 3분 유지했다. 측정 시 활성화한 `?netDebug=1`의 5초 집계 34개 결과:

- 렌더링 집계 FPS: **60.0~60.4**.
- 입력 방향과 반대로 튄 프레임: **0**.
- 측정 구간 중 강제 재동기화: **0**.
- ack에 맞춘 위치 오차의 최대값: **32.7px**. 이 값은 서버의 지연된 현재 좌표와 Sprite의 현재 좌표를 그대로 뺀 값이 아니다.
- 서버 스냅샷은 대체로 20Hz. 이동 입력은 구간별 약 14~17Hz, 정지 구간은 0Hz였다. 일반 보정은 최대 1px/60Hz 프레임으로 제한됐고, 일부 방향 전환 구간에서는 이 보정이 계속 적용됐다. 모든 보정이 사라졌다고 해석하면 안 된다.
- 2분 이동 중 WebSocket 오류·정책 위반 종료 없음. 이후 의도적으로 로컬 중계기를 중지·재시작해 자동 복구를 별도로 확인했다.

수정 전 브라우저 FPS는 측정하지 않았다. 격리 테스트와 브라우저의 측정 조건이 다르므로 두 결과를 같은 실험의 수치로 혼합하지 않는다. 운영 환경의 최종 체감과 다양한 실제 지연은 사용자가 확인한다.

## 회귀 검증

- 프론트엔드 테스트 24개: 실제 Body reset/보정 비교, 8방향 지연 재현, 오래된 ack/예측 기록 누락/큰 오차, 벽·가구 경계, 수신 콜백에서 위치 미변경, POST_UPDATE 한 번 적용 및 리스너 해제, 기존 상호작용·프로토콜·인사·API 테스트.
- Maven 전체 테스트 27회, 실행 JAR 생성 성공. 기존 서버 속도·충돌·입력 빈도·비정상 입력 차단과 연구 HTTP 회귀 포함.
- 로컬 브라우저: 두 방문자 이동 표시, 의자에 막히는 충돌과 우회, 새로고침, 의도적인 연결 단절 후 복구, 복구 후 인사 말풍선, 컴퓨터 E로 연구 기록 조회, ESC로 패널 종료 확인. 테스트 데이터는 DB 없는 로컬 fixture를 사용했다.
- `npm test`, `npm run lint`, `npm run build`, `mvn verify`로 확인했다. 기존 큰 번들 경고는 남아 있다.
- 로컬에 Docker 실행 도구가 없어 로컬 이미지 빌드는 수행하지 못했다. PR CI의 Docker 빌드 결과는 별도로 확인해야 한다.

정상 접속에는 추가 로그가 없다. `?netDebug=1`일 때만 5초마다 `[multiplayer:movement]`에 FPS, 보정 횟수·거리, 강제 동기화, ack 오차, 역방향 프레임, 입력·스냅샷 빈도를 집계한다. 원문 메시지·토큰·개인정보는 출력하지 않는다.

## 운영 확인 범위

PR CI 통과 확인 후 병합한다. CI 실행 결과는 PR에서 확인한다. main 병합 이후 자동 배포 완료 여부와 운영 사이트 체감 테스트는 사용자가 담당한다. SSH 접속, 수동 deploy.sh 실행, 운영 컨테이너 재시작 및 DB 변경은 하지 않는다.

## 2026-11-16 추가 보완: 허용 오차 경계의 미세 진동

사용자가 실행 중인 운영 화면에서 직접 확인하도록 요청하여, 이번에는 운영 브라우저에 접속해 WASD·방향키·대각선·방향 전환을 시험했다. 변경 전 운영 화면의 진단 로그는 약 60 FPS였고 연결 종료 경고는 없었다. 한 5초 구간에서 일반 보정 72회, 총 보정 거리 63.9px, ack 기준 최대 오차 64.4px가 기록됐다. 역방향 프레임은 0이었지만, 이 값만으로 미세한 속도 변동까지 없다고 볼 수는 없다. 운영 서버 접속이나 재시작·배포는 수행하지 않았다.

코드와 격리 테스트에서는 다음 두 경로를 확인했다. 운영에서 보인 모든 미세 진동을 이 두 경로만으로 설명한다고 단정하지는 않는다.

1. 이동 오차가 16px를 넘는 순간 **전체 오차**를 보정 대상으로 삼았다. 60Hz에서 15.9px 오차에는 보정이 없는데, 16.1px에서는 바로 한 프레임 1px를 보정했다. 작은 틱 오차가 허용 경계에서 보정 속도를 갑자기 바꿀 수 있었다.
2. 허용 오차를 서버의 `moving`만으로 선택했다. 로컬에서는 이미 새로 이동하고 있어도, 지연된 서버 정지 상태가 도착하면 정지용 2px 기준이 적용돼 불필요한 보정을 만들었다.

`LocalReconciliation.receive()`가 현재 로컬 입력도 받도록 하고, 서버 또는 로컬 중 하나라도 이동 중이면 기존 16px 기준을 유지했다. 양쪽 모두 정지하면 기존 2px 기준을 쓴다. 보정 벡터는 전체 오차가 아니라 **허용 오차를 초과한 거리**만큼 만든다. 이 방식은 허용 경계에서 보정량이 연속적으로 증가하고, 정지 후에도 허용 영역을 지나쳐 보정하지 않는다. 입력 전송 주기, 서버 검증, 최대 일반 보정 속도 60px/초, 큰 오차 재동기화 및 충돌 제한은 유지했다.

재현 테스트에서 16.1px 오차의 60Hz 한 프레임 보정은 **1px → 약 0.0130px**가 됐다. 이 수치는 동일한 합성 입력의 격리 테스트 결과이며 운영 전후 평균 비교가 아니다. 지연된 정지 상태와 로컬 이동의 조합, 정지 후 단조 수렴, 실제 장면 연결이 로컬 입력을 전달하는 회귀도 확인했다. 추가한 테스트 3개는 수정 전 모두 실패했고 수정 후 통과했다.

수정본 로컬 브라우저에서는 두 방문자를 연결하고 테스트 전용 TCP 중계기로 각 방향 75ms, 추가 RTT 150ms를 적용했다. WASD·방향키·대각선·방향 전환, 컴퓨터 가구에 막히는 충돌, E로 DB 없는 fixture 연구 기록 목록 열기, ESC 종료, 종료 후 이동을 확인했다. 초기 연결을 제외한 **5초 집계 18개(이동과 대기 포함)**에서 FPS 60, 역방향 프레임 0, 강제 동기화 0이었다. ack 기준 최대 오차는 69.2px였고, 필요한 일반 보정은 남아 있다. 정지 후 2px 부근으로 수렴한 구간에는 추가 보정이 없었다. 이 기록은 모든 지연 환경에서 떨림이 사라졌다는 보증이 아니다.

지연 시험 준비 중 별도 개발 포트 5189는 기존 Origin 허용 목록에 없어 연결이 거부됐다. 설정을 완화하지 않고 허용된 5188에서 시험했다. 해당 준비 로그와 초기 연결 동기화는 위 집계에서 제외했다. 운영 설정은 변경하지 않았다.

- 프런트엔드: 테스트 27개, lint, TypeScript 및 Vite 빌드 통과. 기존 번들 크기 경고 유지.
- 백엔드: Maven verify, 테스트 31개 및 실행 JAR 생성 통과. 백엔드 소스 변경 없음.
- 수정본 운영 반영 후의 체감은 미검증이다. 이번에 직접 확인한 운영 화면은 수정 전 버전이다. 이후 자동 배포와 최종 운영 확인은 기존대로 사용자가 진행한다.

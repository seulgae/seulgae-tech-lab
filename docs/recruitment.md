# 서비스 연구실 업무 에이전트

개발 연구실 → 서비스 연구실(office-1)의 아래쪽 컴퓨터 3대 앞에 서치·체크·로그를 배치한다.
기존 위쪽 컴퓨터의 QA·유지보수·운영 게시판과 충돌 영역은 유지한다.
NPC 클릭 또는 E로 실제 업무 현황을 연다. 상세 공고·근거·수동 실행은 관리자 등급 3만 가능하다.

## 실행 구조

외부 LLM과 모델 학습을 사용하지 않는 Java 규칙 기반 업무 에이전트다.
역할(목표)·검색 도구·DB 작업 기억·선행 조건·재시도·결과 보고를 분리했다.
화면의 타이머는 상태 조회만 하며, 브라우저가 없어도 Spring 서버에서 실행한다.

| 한국 시각 | 직원 | 업무 |
|---|---|---|
| 09:00 | 서치 | Brave Search API로 사람인·잡코리아 공고 URL·발췌문 수집 |
| 13:00 | 체크 | 기업정보 확인 단서 검색(최대 3개 후보), 필수 근거와 조건 검증 |
| 15:00 | 로그 | 기업·후보 공고·출처의 멱등 등록 및 갱신 |
| 17:00 | 로그 | 활성 공고 최대 10개 재검색, 검증·등록, 확인된 마감 처리·보고 |

검색 API의 제목에서 대괄호 기업명을 단서로 가져오되 확인된 기업정보로 취급하지 않는다.
검색에서 공고가 누락되거나 조회가 실패해도 종료하지 않는다. 발췌문에 평점·인원이 있어도 확정 사실로 승격하지 않는다.
필수 정보가 없으면 REVIEW다. 관리자 근거 보완 화면에서 원문 확인 후 값·URL·인용문을 입력한다.
근거가 모두 있으면 Java가 조건을 비교해 ELIGIBLE/REJECTED로 분류한다. 수습 미기재는 통과가 아니다.
즉, 원문이 공개되지 않은 정보까지 완전 자동으로 확인하는 시스템은 아니다.

## 초기 설정

1. 스키마 확장 PR 병합·11..12 릴리스 배포 성공을 확인한다.
2. 운영자가 기존 절차대로 `python3 deploy/migrate-prod.py`를 실행해 V12를 적용한다.
3. 기능 PR을 병합한다. 기능 릴리스 호환 범위는 12..12다.
4. [Brave Search API](https://brave.com/search/api/)에서 검색용 토큰을 발급받는다. OpenAI 키는 필요 없다.
   사용량·요금·검색 결과의 저장 및 표시 허용 범위는 신청한 플랜에서 확인한다.
5. 기존 secrets 디렉터리에 소유자만 읽는 `recruitment.env` 파일을 만든다(예: chmod 600).

```dotenv
LAB_RECRUITMENT_ENABLED=true
LAB_RECRUITMENT_SEARCH_KEY=발급받은_검색_API_토큰
```

이 파일은 저장소에 넣지 않는다. 파일이 없으면 모듈은 기본 비활성이고 기존 서비스는 계속 동작한다.
운영자가 설정 후 기존 배포 절차로 컨테이너에 반영한다. 이 작업에서 운영 서버 접속·배포·DB 변경은 수행하지 않는다.
개발 환경에서는 같은 이름의 환경변수로 설정한다. 공급원 키가 없으면 UNAVAILABLE이며 가짜 공고를 생성하지 않는다.

## 상태·재시도·복구

전용 예약 스레드가 1분마다 도래한 업무를 확인한다. 기본 웹소켓 예약 스레드와 분리되어 있다.
한국 날짜·업무 종류 UNIQUE와 PostgreSQL 세션 advisory lock으로 여러 인스턴스·수동 실행을 직렬화한다.
정책 시작일은 V12 적용의 한국 날짜다. 재시작하면 이 날짜부터 미완료 업무를 시간순으로 한 업무씩 보완한다.
과거 공고를 복원하는 기능은 아니다. 보완 수집도 현재 검색 결과를 저장한다.
선행 업무가 실패하면 후속 업무는 대기한다. 실패는 15분 간격 최대 3회 자동 시도하고 이후 관리자가 재시도한다.
대시보드의 실패 업무 재시도는 과거 날짜도 지원한다. 완료한 업무의 중복 수동 실행은 409로 거부한다.
DB에는 업무별 최종 상태·시도 횟수·시작/종료·오류를 보존한다(개별 시도 전체 로그를 별도 저장하는 구조는 아니다).

## 데이터 관리의 범위

- 원본 출처+공고 ID를 UNIQUE로 관리한다. 같은 공고를 재검색해도 중복 등록하지 않는다.
- 확인하지 않은 기업명은 공고별 임시 기업 키로 구분한다. 이름 유사도만으로 서로 다른 기업·공고를 합치지 않는다.
- 다른 사이트의 유사 공고를 자동으로 하나로 합치는 기능은 아직 없다. 원본 연결을 유지한다.
- 마감일 또는 직접 확인된 접수 종료 근거가 있는 공고만 EXPIRED로 바꾼다. 물리 삭제하지 않는다.
- 활성 추천 목록은 ELIGIBLE+ACTIVE만 표시한다. REVIEW·REJECTED·EXPIRED는 별도 필터로 볼 수 있다.
- 수동 근거는 재수집 때 유지한다. 근거 유효기간은 30일이며 이후 다시 REVIEW로 분류한다.
- 검색은 출처별 첫 20개 결과, 현행화는 오래 확인하지 않은 활성 공고 10개다. 전체 채용시장의 완전 수집을 보장하지 않는다.
- 검색 단서·수동 입력 UI는 코드 실행이나 임의 SQL 실행을 제공하지 않는다.

## API

- `GET /api/recruitment/agents`: 공개된 오늘의 최소 업무 상태(상세 오류·공고 제외).
- `GET /api/recruitment`: 관리자 대시보드, 최근 공고 100개·업무 40개·보고서 7개.
- `POST /api/recruitment/jobs/{SEARCH|CHECK|REGISTER|REPORT}?date=YYYY-MM-DD`: 관리자 수동 실행.
- `PUT /api/recruitment/collections/{id}/evidence`: 관리자 원문 근거 보완 및 재검증·등록.

수동 근거 보완도 정기 작업과 동일 DB 락을 사용한다. 정보 출처는 허용한 HTTPS 도메인으로 제한한다.
검증 테스트의 가짜 공고는 테스트 디렉터리에서만 생성한다. 실제 외부 호출·API 키는 테스트에 사용하지 않는다.

## 검증 방법

프론트 `npm test`, `npm run lint`, `npm run build`와 백엔드 `mvn -f backend/pom.xml verify`를 실행한다.
CI는 일회용 PostgreSQL에 V12까지 적용하고 `RECRUITMENT_TEST_DB=true`로 실제 저장·락·업무 순서·만료·재시도를 검증한다.
로컬에 Docker/PostgreSQL이 없으면 DB 통합 테스트는 건너뛰며 CI 결과를 확인한다.
로컬 브라우저에서 개발 연구실→서비스 연구실 이동, 직원 3명 배치, NPC 클릭 상세 패널과 닫기를 확인했다(백엔드 없는 비로그인 상태). 관리자 대시보드 실화면·실제 검색 품질·발급 토큰·운영 스케줄·운영 반영은 별도 확인 대상이다.
